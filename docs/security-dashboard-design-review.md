# 보안 현황·기술 생태계 대시보드 설계 검토

검토일: 2026-11-11. 범위: 로컬 코드와 저장 데이터, 공식 시각화 문서 검토. 운영 기능 구현·배포 또는 기사 사실관계 재검증은 포함하지 않는다.

## 1. 결론

추가할 것은 큰 관계도 하나가 아니라, 같은 이슈 데이터를 목적에 맞게 보는 두 화면이다.

| 화면 | 사용자가 답을 얻는 질문 | 기본 시각화 |
| --- | --- | --- |
| 보안 현황 | 지금 어느 영역에서 무엇이 바뀌었나? | 영역별 변화 매트릭스 + 중요한 변화 3건 |
| 기술 생태계 | 이 제품·기술에 어떤 이력이 있고 무엇과 연결되나? | 위치가 고정된 분류 지도 + 선택 대상의 이력 |
| 기존 최신 기사 | 새로운 원문을 빠르게 훑어볼 수 있나? | 기존 이미지 기사 행 유지 |

세 번째 거대 그래프를 추가하지 않는다. 계정·SaaS, 단말·브라우저, 개발·공급망, 클라우드·서버, 네트워크·장비, 데이터·제도라는 **보안 영역**으로 전체를 포괄한다. AI는 여러 영역에 걸치는 태그다. OT·IoT 등은 처음에는 네트워크·장비의 하위 영역으로 두고 실제 자료량과 탐색 요구에 따라 분리한다.

공개 뉴스로 만드는 것은 '공개 보도 기반 보안 현황'이다. 내부 자산·노출도 확인이 없으므로 실제 ASM이나 우리 조직의 위험도라고 표현하지 않는다.

## 2. 현재 기반과 제약

로컬 `data/events.jsonl`에서 빈 URL 제외, 같은 URL은 파일에서 마지막 레코드 유지, `common_utils.NON_NEWS_SOURCES` 제외 기준으로 집계했다. URL 중복 제거는 동일 사건 중복 제거와 다르다.

| 항목 | 확인 결과 |
| --- | --- |
| 기사형 소스의 서로 다른 URL | 10,400건 |
| 기술동향·제품행사·정책규제 URL | 4,477건 |
| 위 정보성 기사 중 affected_products가 비어 있지 않은 URL | 1,598건, 약 35.7% |
| 일간 저장 JSON | 94개, 파일명 범위 2026-07-26~2026-11-10 |
| 주간 저장 JSON | 17개 |
| 최신 기사 피드 | 최근 수집 14일, 최대 300건 |
| 검색 인덱스 | 10,320개 레코드, 코드상 보관 기간 365일 |

주의: 기간 양 끝이 있다고 모든 날짜의 수집이 완전한 것은 아니다. 발행일, 수집일, 사건 발생일은 다르다. 정보성 기사에 제품명이 없는 것은 반드시 오류가 아니지만, 그 필드만 쓰면 정책·연구·표준·개념 자료가 지도에서 누락된다. 집계 숫자는 데이터 규모이며 사실 확인이나 위험 수준을 뜻하지 않는다.

### 중요한 발견

- `scripts/live_news.py:15`: 최신 피드는 300건·14일로 제한된다. 수개월 이력을 이 파일에서 만들면 안 된다.
- `scripts/live_news.py:77`: 공개 기사에는 제목·요약·분류·시간이 있지만 엔티티 관계가 없다.
- `scripts/generate_report.py:2719`: 일간 기사 직렬화에도 제품 엔티티·관계 정보가 없다. 브라우저에서 매번 제목을 다시 분류하는 구조는 피한다.
- `scripts/publish_web_dashboard.py:182`: 검색 인덱스는 원시 이벤트에서 재구성되지만, 요약은 200자로 제한되고 관계 근거를 보존하지 않는다.
- `scripts/common_utils.py:942`: affected_products는 영향받는 제품 중심이다. 정보성 기사의 주제 엔티티는 별도 필드로 추출해야 한다.
- 기존 최신 화면은 `dashboard/assets/app.js`의 추천·주제·출처·AI·캠페인 행을 재사용한다. 새 대시보드에 이를 전부 다시 쌓지 않는다.

## 3. 보안 현황 화면

### 첫 화면

1. 제목·집계 기간·마지막 성공 수집 시각. 기간 선택은 24시간/7일/30일로 제한하고 기준을 명확히 한다.
2. 중요한 변화 최대 3건. '무엇이 달라졌는지 / 관련 대상 / 확인할 것'만 짧게 표시한다.
3. 보안 영역 × 변화 유형 매트릭스. 행은 6개 보안 영역, 열은 공격·사고 / 패치·지원 / 기능·정책이다. 영역은 여러 개를 가질 수 있고 한 사건은 합계에서 중복 계산하지 않는다.
4. 선택한 영역의 이슈 이력·원문·이미 존재하는 심층분석 연결. 세부 내용을 처음부터 전부 펼치지 않는다.

색은 심각도가 아니라 명시된 변화 유형을 나타낸다. 기본 화면은 도메인별 대표 변경과 짧은 제목으로 읽히게 한다. 이슈 수를 표시한다면 중복 제거된 사건 수임을 밝히고 기사 수와 분리한다. 미수집·갱신 실패는 '새 소식 없음'과 다르게 표시한다.

### 우선순위

임의의 AI 종합 위험 점수 대신 검증 가능한 근거를 우선한다. 공식 확인된 악용·영향 변경, 실제 지원 종료·적용 기한, 신규 패치/완화책, 그 다음 보안 관련 기능·연구 순으로 제시한다. 실제 이용 여부는 알 수 없으므로 '영향받음' 대신 대상과 조건을 명시한다. 제품 출시와 마케팅 발표에 대응 의무를 부여하지 않는다.

지속되는 사건은 새 기사 한 건마다 '신규'로 표시하지 않는다. 최초 발견, 영향 범위 확대, 공격 확인, 패치 공개, 정정 등 **변경된 주장**이 있어야 갱신 항목으로 올린다. 동일 기사 재수집·요약 재생성은 신규 사건이 아니다.

## 4. 기술 생태계 화면

### 고정된 공간 + 선택적 관계 확장

- 개발 도구 / 패키지·마켓플레이스 / 확장프로그램 / AI·연결 / 배포·실행 / 웹 기술의 여섯 영역.
- 각 영역에 대표 엔티티 몇 개만 노출한다. 나머지는 해당 영역을 펼치거나 검색해서 접근한다. 위치를 매번 임의로 바꾸지 않는다.
- 기본 범위 90일, 180일·전체 보유 기간으로 확장. 실제 수집 범위를 별도 보존한다.
- 노드 선택 시 주변 1단계 관계만 표시한다. 관계 명칭과 출처를 볼 수 있어야 한다.
- 상세는 최신 변경 요약 → 발행일 기준 이력 → 적용 조건·관련 원문 순서. 근거가 없는 현재 상태나 대응 완료를 생성하지 않는다.
- NVD·MSRC 원시 목록은 기본 지도에 넣지 않는다. 선택 제품과 명확히 연결된 CVE/공격은 필요할 때 보안 이슈로 열어볼 수 있다.
- 모바일에서는 같은 카테고리와 엔티티를 세로로 배치한다. 큰 캔버스를 축소해서 작은 글씨로 읽게 하지 않는다.

AI 코딩 도구와 브라우저 확장처럼 여러 영역에 속하는 엔티티는 동일 ID를 재사용한다. 표시 위치는 대표 영역으로 정하고 다른 영역에서는 연결로 접근한다. 이름이 같은 공급자·제품·프로토콜을 한 노드로 합치지 않는다.

### Gemini 제안에서 바꿀 부분

| 제안 | 검토 |
| --- | --- |
| Vendor → Asset → Threat → Article 계층 | 탐색 순서로는 가능하지만 실제 데이터는 다대다다. 기사 하나가 여러 제품을 다루고, 정보성 기사에는 위협 자체가 없을 수 있다. |
| 모든 것을 네트워크 그래프로 표시 | 관계가 많아질수록 라벨과 연결선이 겹친다. 전체 분류는 고정 배치하고 관계망은 선택 대상에 한정한다. |
| 기사만으로 내 인프라 영향 파악 | 관심 기술 탐색까지는 가능하다. 실제 영향 판정에는 자산·버전·설정·노출 근거가 별도로 필요하다. |
| Neo4j/FastAPI/React 도입 | 현재 목적에서는 필수 아님. 기존 Python 집계와 정적 JSON/JS를 유지한다. |

## 5. 공통 데이터 모델

기존 category 하나를 대체하지 말고 보완한다. 원본은 변경하지 않고 파생 데이터로 생성한다.

| 객체 | 핵심 필드 |
| --- | --- |
| Entity | id, canonical_name, aliases, entity_type, ecosystem_areas, security_areas |
| Article | ref, canonical_url, source, published_at, collected_at, content_quality, entity_mentions |
| Issue | id, issue_type, entity_ids, title, first_reported_at, last_material_change_at, source_refs |
| Change | id, issue_id, change_kind, occurred_at, effective_at, reported_at, date_precision, claim, evidence_ids |
| Relation | id, from_id, to_id, relation_type, valid_from/to, evidence_ids, review_status, extraction_method |
| Evidence | id, article_ref, source_url, short_excerpt, retrieved_at, content_hash, source_kind |
| Coverage | source/category, last_success_at, available_from/to, collection_gaps, classification_version |

엔티티 유형: vendor, product, project, package, extension, platform, protocol, standard. `affected_products`와 달리 제품 홍보·표준 변경에도 `entity_mentions`를 붙일 수 있다.

관계 유형 예: publishes, distributed_via, integrates_with, depends_on, affects. `depends_on`은 공식 문서/매니페스트 등 직접 근거가 있을 때만 채택한다. 같은 문장에 등장하는 것만으로 의존 관계를 만들지 않는다. LLM 제안·추론은 기본 관계 지도에서 제외하고 검토 대기 목록으로 보낸다.

날짜를 모르면 null로 둔다. 수집일을 지원 종료일이나 사건 발생일로 대체하지 않는다. 기사 발행일 이력과 실제 적용 기한을 서로 다른 시각 표식으로 구분한다.

## 6. 무료 운영에 맞춘 처리

`events.jsonl → 공개 필드 정제 → 엔티티 정규화 → 기사/사건 중복 정리 → 변화·관계 검증 → 파생 JSON → 정적 대시보드`

1. 대표 엔티티 30~50개 별칭 사전으로 시작한다. 전체 기술 생태계를 처음부터 완성하려 하지 않는다.
2. 최근 90일을 먼저 백필하되 180일·이전 데이터도 같은 코드로 처리할 수 있게 한다. 과거 날짜의 분류 체계가 다르면 버전을 명시한다.
3. 기존 구조화 필드·제목·본문의 정확한 별칭 매칭을 먼저 사용한다. 문맥이 필요한 동명이인/동명제품은 보류한다.
4. 불명확한 자료만 기존 무료 LLM에 소량 요청한다. URL·본문 해시·분류 버전 캐시, 호출 상한, 실패 보류를 둔다. 화면 조회 자체는 LLM 호출 없이 동작한다.
5. 본문 없이 제목·짧은 요약만 있으면 엔티티 탐색 후보로는 쓸 수 있지만 관계 확정에는 쓰지 않는다.
6. 신규 수집 때 변경된 엔티티/사건만 갱신한다. 요약 품질 저하·분류 실패가 생겨도 마지막 정상 산출물을 유지한다.
7. 엔티티/월별 상세 JSON을 지연 로딩하고 초기 화면에는 요약 인덱스만 보낸다. 중복된 전체 원시 데이터는 브라우저에 내려보내지 않는다.

공개 내보내기는 허용 필드 목록 방식. matched_assets, pirs, 내부 운영환경·자산 소유 정보는 구조화 필드와 문장 모두에서 제외한다. 관심 제품 저장은 필요해진 이후 사용자 로컬 설정으로 설계하고 공개 자산 목록과 섞지 않는다.

## 7. 개발 범위와 통합 지점

### 1차: 데이터 기반

`boannews_mail`에 엔티티 사전, 정규화/이력 집계 모듈, 오프라인 백필·검사 스크립트 추가. 기존 수집기나 심층분석을 강제 재실행하지 않는다. 발행 성공 직전 파생 JSON 생성 단계를 연결하고 실패 시 기존 정상 파일을 유지한다. 이 단계에서는 모든 관계를 자동 확정하지 않는다.

### 2차: 화면

`boannews_vercel_deploy/dashboard`에 보안 현황·기술 생태계 렌더러를 별도 모듈로 추가. 공통 페이지 제목, 원문 링크, 인사이트 연결, 색상·포커스·반응형 스타일을 재사용한다. 기존 최신 기사 카루셀과 로딩 동작은 유지한다.

최초에는 `대시보드` 진입점을 만들고 그 안에 `보안 현황 | 기술 생태계` 두 보기를 둔다. 검증 전에는 현재 기본 진입 화면을 바꾸지 않는다. 상위 탭을 계속 늘리지 않으며 기존 일간/주간·CVE·인사이트·아카이브 경로도 제거하지 않는다. 장기적으로 탐색/보고서/기록 묶음 정리는 별도 UI 작업으로 합의한다.

### 3차: 관계·검증 강화

공식 릴리스 노트, 제품 지원 정책, 마켓플레이스 공지처럼 현재 뉴스에 부족한 자료를 필요한 엔티티부터 수집한다. 기존 수집 이력만으로 웹 표준·IDE 확장 생태계를 완전하게 커버한다고 표시하지 않는다. 공지 소스의 이용 조건·요청 제한을 확인하고 원문 전체 재게시 대신 짧은 요약과 링크를 제공한다.

관계도가 실제로 필요해진 상세 화면에는 Cytoscape.js를 사용한다. React Flow를 쓰기 위해 기존 앱을 React로 전환하지 않는다. Neo4j는 다단계 관계 질의·서버 협업 편집 등 정적 JSON으로 다루기 힘든 요구가 생길 때 재검토한다.

## 8. 완료 기준

- 사용자가 10초 내 주요 변화, 관련 영역, 다음 확인 위치를 지목할 수 있는지 실제 관찰한다. 미리 '10초 달성'으로 주장하지 않는다.
- 대표 엔티티 30개, 수작업 검토 기사 100개로 연결 정확도/누락률을 측정한다. 출시·정책·공격·패치·오분류/동명이인·수집 실패를 포함한다.
- 공개되는 확정 관계는 전부 출처와 짧은 근거를 갖고, 무근거 의존 관계는 0건이어야 한다.
- 동일 기사 재수집과 같은 발표의 복수 보도는 새로운 이슈 수를 늘리지 않는다. 실질적 후속 발표는 같은 이슈의 변경 이력으로 남는다.
- 320/390/1024/1440px, 라이트/다크, 키보드 선택, 돌아가기, 긴 이름, 빈 결과, 실패 후 이전 데이터 유지 확인.
- 초기 화면은 관계 라이브러리·모든 이력을 먼저 내려받지 않는다. 탭 활성 상태는 즉시 바뀌고 데이터 로딩/실패는 해당 영역에 표시한다.
- 파생 JSON은 기존 `check_dashboard_quality.py`와 별도 엔티티·관계 무결성 검사로 확인한다. 데이터 품질 검사와 사실 검증을 혼동하지 않는다.
- 비용 검증: 대시보드 조회 시 모델 호출 0회. 백필/증분 작업은 호출 수·보류 수를 기록하고 제한을 지킨다.

## 10. 이번 검토 산출물과 확인 범위

대화 내 초안은 보안 영역별 매트릭스, 기술 분야별 고정 배치, 항목 선택에 따른 저장 기사 이력과 검토 지점을 보여준다. 현재 위험도, 실시간 추이, 전체 집계 또는 검증된 제품 간 관계도를 구현한 것은 아니다. 상단 주요 변경 3건·기간 필터·관계 확장은 위 설계에 포함되지만 이번 화면 표본에는 포함하지 않았다.

Edge/Playwright로 1024/390/320px에서 두 보기 전환, 항목 선택, 빈 자료, 원문 링크 형식, 가로 넘침을 점검했다. 라이트·다크 렌더링과 키보드 Enter 활성화도 확인했다. 클릭할 외부 기사의 사실관계 재검증과 실제 사용자의 10초 인식 테스트는 하지 않았다. 운영 코드와 기존 수집 데이터는 변경하지 않았다.
